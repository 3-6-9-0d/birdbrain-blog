Finding Bugs in Fusion Drinks: How a Promotional QR Code Exposed Production PII

Posted by Security Researcher • Case Study

What started as a completely ordinary visit to Mouzy, a fusion drink outlet, turned into an unexpected security assessment.

After paying, the cashier handed us a small card with a QR code and told us we could play a game called Zuzy Run to win rewards. Most people would scan the QR code, play the game, and move on. I scanned it and had a different thought:

“I wonder how secure this is.”

That thought kicked off an unexpected security assessment that eventually led to the discovery of a critical Firebase misconfiguration exposing sensitive production data.

The Target

The QR code redirected to:
https://zuzyrun.gamefaktory.com/?token=...

The application was a browser-based game where players used limited “hearts” (lives) to play and accumulate points for rewards. At first glance, it looked like a typical promotional game. But while interacting with it, a few things immediately felt off:

  • Client-side logic seemed heavy
  • Session state appeared stored locally

That usually means one thing: Interesting things may be happening in the frontend.

Initial Recon

I started with standard passive recon:

  • Browser DevTools
  • Network inspection
  • Source code inspection
  • Local storage review

The frontend bundle exposed a Firebase configuration object: 

const firebaseConfig = {
  apiKey: "...",
  authDomain: "",
  projectId: "",
  storageBucket: "...",
  messagingSenderId: "...",
  appId: "..."
}

Now, an exposed Firebase API key alone is not automatically a vulnerability. Firebase client configs are often public by design. The real question is: Are backend security rules correctly configured? That became the focus.

Firestore Enumeration

From the JavaScript bundle, I identified the Firebase project. That enabled testing Firestore’s REST API. Firestore document paths follow this structure: 

https://firestore.googleapis.com/v1/projects/PROJECT_ID/databases/(default)/documents/COLLECTION

I began testing likely collection names referenced in the frontend. That’s when things got serious.

Critical Findings

Critical Finding #1: Unrestricted Player Data Access

The following endpoint returned data without authentication: 

https://firestore.googleapis.com/v1/projects/zuzu-run/databases/(default)/documents/players?pageSize=100

This exposed player records containing:

  • Names
  • Phone numbers
  • Scores
  • Gameplay metadata

This is personally identifiable information (PII). At this point, the issue was no longer theoretical. Unauthorized users could enumerate real user data directly from Firestore.

Critical Finding #2: Token Exposure

Another collection was readable:

https://firestore.googleapis.com/v1/projects/zuzu-run/databases/(default)/documents/tokens?pageSize=300

This exposed active gameplay tokens. These tokens were tied to QR sessions and controlled access to game lives (hearts).

By obtaining valid tokens, an attacker could:

  • Reuse active game sessions
  • Gain additional hearts
  • Continue playing indefinitely
  • Potentially abuse reward mechanisms

This transformed a simple data leak into a practical exploitation path.

Critical Finding #3: Admin Collection Exposure

The most alarming discovery was:

https://firestore.googleapis.com/v1/projects/zuzu-run/databases/(default)/documents/admins

This exposed administrator records, including:

  • Admin names
  • Gmail addresses

Even though passwords were not exposed, leaking admin identities significantly increases attack surface for phishing, credential stuffing, and social engineering.

Impact

The Firestore rules effectively allowed unauthenticated read access to sensitive collections. An attacker with basic Firebase knowledge could read player PII, enumerate admin accounts, harvest active tokens, abuse gameplay mechanics, and potentially manipulate rewards. Depending on write permissions, the impact could have escalated further.

Metric Value
Severity Assessment CRITICAL

Responsible Disclosure

I stopped immediately after confirming the scope. I did not:

  • Dump the database
  • Store user data
  • Share any records
  • Attempt destructive actions

Instead, I drafted a disclosure report and contacted the vendor. My report summarized the vulnerability type, affected collections, impact, reproduction steps, and risk assessment.

Vendor Response

To their credit, the response from GameFaktory was extremely fast and professional. They acknowledged the issue, accepted responsibility, and began remediation quickly. That is exactly how responsible disclosure should work.

Lessons Learned

1. Public Firebase config is not the problem

Many developers panic when they see exposed Firebase keys. That’s usually not the issue. The issue is almost always: Bad Firestore security rules.

2. Frontend code reveals architecture

Even minified JavaScript leaks valuable information: Collection names, Project IDs, API endpoints, and Business logic. Attackers use these clues. So should defenders.

3. Small apps need security too

This wasn’t a banking app. It was a promotional game. Yet it still handled user identities, rewards, admin accounts, and PII. Even “simple” systems need proper access control.

Final Thoughts

This bug started with something ordinary: A QR code on a card handed over with milk products. That tiny moment turned into a real-world security assessment and a critical finding. Security issues rarely announce themselves dramatically. Sometimes they begin with a simple instinct: “Something feels off.”
